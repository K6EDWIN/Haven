# Haven: A Privacy-First Safe Space AI

<img src="mobile/public/brand/github-icon.png" width="180" alt="Haven GitHub mark" />

**Haven** is a Python-based mental health companion designed to act as a supportive listening ear. It prioritizes user privacy by offering an ephemeral "safe space" for venting without data permanence, while also providing optional tools for mood tracking and professional resource connection.

## 📖 Project Overview

Haven was built on the belief that everyone deserves a non-judgmental space to talk. It operates in two distinct modes:
1.  **Safe Space Mode:** A private, real-time conversation loop where your thoughts are heard but **never recorded**.
2.  **Check-In Mode:** An optional tracking feature that allows you to log interactions, monitor sentiment trends, and schedule appointments if you choose to do so.

## ✨ Key Features

* **Ephemeral "Safe Space" Loop:** A dedicated mode that allows you to converse with the AI without any data being saved to the database. It is designed purely for the moment.
* **Sentiment Analysis:** Powered by **TextBlob**, Haven analyzes your input to detect emotional polarity (positive/negative) and responds with appropriate empathy.
* **Entity Extraction:** Uses **spaCy** to identify key subjects and context within your sentences.
* **Resource Hub:** Provides immediate access to vetted mental health resources (CDC, NIMH, etc.) for topics like anxiety, trauma, and depression.
* **Appointment Scheduling:** A built-in system to book and log appointments with counselors securely.
* **Optional Saved Check-ins:** Uses **Flask-SQLAlchemy** when you choose to save a check-in.

## 🛠️ Tech Stack

* **Language:** Python 3.x
* **Frameworks:** Flask, Flask-SQLAlchemy
* **NLP Engines:** TextBlob, spaCy (`en_core_web_sm`)
* **Database:** SQLite locally, Neon/PostgreSQL with `DATABASE_URL`, or legacy Turso/libSQL with `TURSO_DATABASE_URL` and `TURSO_AUTH_TOKEN`
* **Interfaces:** Flask routes, a command-line interface, and the Android app

## Android app

The mobile interface lives in `mobile/` and is built with React, Vite, and Capacitor. It connects to the Flask API for Safe Space replies, saved check-ins, resource links, and appointment request records. Safe Space messages remain temporary. Check-ins are saved by the backend and a local copy is kept on the device for the check-in screen.

To build an Android APK from GitHub Actions, add a repository secret named `HAVEN_API_BASE_URL` containing the public base URL of the deployed Haven Flask service (for example, `https://your-haven-service.example.com`, without a trailing slash). A push to `main` or a `codex/*` branch that changes the mobile app or API starts **Build Haven Android APK**. The resulting `haven-android-debug-apk` artifact can be downloaded from that workflow run. The workflow can also be started manually from the Actions tab.

For local mobile development, set `VITE_API_BASE_URL` in `mobile/.env.local` to the same deployed API base URL, then run `npm install` and `npm run dev` from `mobile/`. Android project files are generated by Capacitor during the APK workflow.

## Haven Console and accounts

The user web app is in `web/` (Next.js) and the mobile app is in `mobile/` (React, Vite, Capacitor). Both use the same Flask API. The Haven Console is served by Flask at `/admin`. It reports actual request volume, HTTP 5xx rate, response latency, endpoint totals, and recent request outcomes. The API also exposes protected account summaries and admin audit records; no private conversation or diary content is included. The current model remains the TextBlob/rule-based implementation, so the console does not claim custom-model quality or provider costs.

Create the first administrator from the deployment shell with `flask --app app create-admin`; this prompts for an email and password without writing them to logs. Admin accounts use the same login endpoint as users and have server-checked roles. Existing `HAVEN_ADMIN_TOKEN` deployments are accepted as a migration fallback; create an admin account and remove the shared token when ready. Set `HAVEN_ALLOWED_ORIGINS` to a comma-separated list of exact HTTPS web origins in production. Local development allows `localhost:3000` and the Capacitor development origins.

Operational metrics are written to a separate `api_request_metrics` table and exclude request bodies, replies, user IDs, and IP addresses. They are pruned to a 30-day window on subsequent API writes. Admin audit records contain actor, action, target ID, outcome, and time only. Never paste private diary or conversation content into operational notes.

### Accounts and private data

Register at `POST /api/auth/register` or sign in at `POST /api/auth/login` with email and a password of at least 12 characters. The API returns an opaque bearer token; store it securely in production clients and send it as `Authorization: Bearer …`. Sessions expire after 30 days and can be revoked with `POST /api/auth/logout`. Passwords and optional account PINs are PBKDF2-HMAC-SHA256 hashes.

Safe Space chat requests remain transient. `POST /api/conversations` persists messages only after an explicit save action; every list, read and delete query is scoped to the authenticated owner. Diary endpoints (`GET/POST /api/diary`, `PATCH/DELETE /api/diary/:id`) enforce the same ownership rule. Existing anonymous check-in records created before account support remain in the legacy `chatbot_interactions` table; new check-ins and appointment requests bind to the authenticated account instead of trusting a client-supplied user ID. New tables are created by SQLAlchemy at app startup; existing deployments should take a database backup before rollout.

For local web development, set `NEXT_PUBLIC_HAVEN_API_URL` in `web/.env.local` and add that exact origin to `HAVEN_ALLOWED_ORIGINS` on Flask. Then install dependencies and run the Next.js development script from `web/`. Configure `HAVEN_API_BASE_URL` in the Android Actions repository secrets for APK builds. A Neon project and production secrets still need to be created in their respective dashboards. The repository does not include a separate custom model or WebAuthn/biometric enrollment; the six-digit mobile lock uses account-backed PIN verification and a client-side inactivity gate.
